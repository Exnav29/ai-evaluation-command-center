This is the Phase 3 Operator Dashboard V1 implementation qualification benchmark.

Work only inside this repository snapshot.

Read and follow:
- docs/ARCHITECTURE_BASELINE_V1.md
- docs/OPERATOR_DASHBOARD_V1_SPEC.md

- docs/TOOL_SKILL_SUBAGENT_EVALUATION_V1.md

Build the first real Operator-facing dashboard on top of the existing Phase 2 evidence foundation.

Required stack:
- Python
- FastAPI
- Jinja2
- server-rendered HTML
- SQLite through the existing SQLAlchemy foundation
- pytest

Required routes:
- GET /operator
- GET /operator/runs/{run_id}
- GET /operator/qualifications

The dashboard must query persisted evidence. Do not build a static mockup or hard-code production route data.

Preserve evidence semantics:
- UNKNOWN must remain distinct from PASS/success;
- process outcome, deliverable outcome, task outcome, and evaluator verdict remain separate;
- exit code 0 is not proof of task success;
- missing cost/tokens are unknown/not recorded, not zero;
- latest score and qualification decisions must be selected deterministically while history remains visible;
- qualification is specific to harness + model + capability;
- excluded/intervention evidence remains inspectable.

Provide deterministic seed/test data exercising both success and failure/unknown/history cases described in the spec.

Use available skills and subagents only when they materially help. Tool volume is not a goal. If you delegate, give the subagent a bounded task, integrate the result, and verify consequential claims. If an optional tool/skill/subagent is denied or unavailable, recover and continue when possible.
